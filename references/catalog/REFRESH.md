# 카탈로그 갱신 절차

사용자가 "카탈로그 갱신해줘", "웹 디자인 쪽 최신으로 다시 조사해줘", "새 분야 추가해줘"라고 하면 이 절차를 따른다. 목표는 **그날 기준으로 다시 검증된 카탈로그**다. 지난번 결과를 믿고 넘기지 않는다.

## 원칙

- **1차 출처만 근거로 쓴다.** 공식 문서, 도구의 GitHub 저장소, 공식 마켓플레이스(anthropics/skills, anthropics/claude-plugins-official, MCP 레지스트리)를 본다. 블로그, SNS 글, awesome 목록은 후보를 찾는 데만 쓰고 근거로 삼지 않는다.
- **직접 확인한 것만 적는다.** 별 수, 마지막 업데이트, 라이선스는 GitHub API로 그날 확인한다. 모르는 값은 `null`로 둔다. 숫자를 지어내지 않는다.
- **설명은 내 말로 쓴다.** README 문단을 옮기지 않는다. 설치·확인 명령만 원문 그대로 적는다.
- **조사 중에는 아무것도 설치하지 않는다.** 남이 만든 스킬은 Claude와 같은 권한으로 돈다. 설치는 사용자가 레시피 단계에서 승인했을 때만 한다.
- **별 수로 순위를 매기지 않는다.** 관리 상태, 겹침, 비용, 위험, 그리고 실제로 써 본 경험(레시피의 "써 보니")을 함께 본다.

## 파일

| 파일 | 내용 |
|---|---|
| `catalog/<area>.yaml` | 분야별 도구 목록. 형식은 `SCHEMA.md` |
| `catalog/SCHEMA.md` | 항목마다 들어가는 키와 뜻 |
| `catalog/research-prompt.md` | 분야별 조사 에이전트에게 주는 지시문 틀 |
| `catalog/CHANGELOG.md` | 갱신할 때마다 무엇이 들어오고 빠졌는지 |
| `recipes/<area>.md` | 도구를 엮는 순서와 단계별 확인 기준 |
| `scripts/check_catalog.py` | 형식 검사와 저장소 관리 상태 점검 |

## 절차

1. **기준일과 범위를 정한다.** 오늘 날짜를 기준일로 쓰고, 갱신할 분야를 정한다(기본: 지금 있는 모든 `catalog/*.yaml`).
2. **분야마다 조사 에이전트를 하나씩 병렬로 띄운다.** `research-prompt.md`의 틀에 분야, 기준일, 꼭 다시 확인할 도구(지금 카탈로그의 id 목록과 레시피에 쓰인 도구)를 채워 넘긴다. 결과는 작업 폴더(스크래치패드)에 YAML과 메모로 받는다.
3. **기계 검사를 돌린다.**
   ```bash
   python scripts/check_catalog.py --validate <받은 yaml>
   python scripts/check_catalog.py --freshness <받은 yaml>
   ```
   `--validate`는 키 누락과 형식을, `--freshness`는 GitHub API로 보관(archived) 여부와 마지막 push가 180일 넘었는지를 본다.
4. **사람이 검수할 곳을 짚는다.** 설치 명령이 공식 문서와 같은지, `overlaps`가 서로 맞물리는지, `risks`에 권한·유료·외부 전송이 빠지지 않았는지 본다. 지난 카탈로그와 비교해 빠지는 도구가 있으면 이유를 적는다. 분야를 따로 조사하면 같은 도구가 여러 파일에 나온다(첫 조사 때 5개). 가장 많이 쓰이는 분야 파일 하나에만 두고 다른 분야는 `also`에 적은 뒤, 내용(위험, 설치 대안)을 합치고 다른 항목의 `overlaps`가 가리키던 옛 id를 새 id로 바꾼다.
5. **카탈로그를 바꾼다.** `catalog/<area>.yaml`을 새 결과로 바꾸고 `CHANGELOG.md`에 기준일, 추가, 제외(이유), 바뀐 설치 방법을 적는다. 바꾼 뒤에는 인자 없이 `python scripts/check_catalog.py --validate`를 돌린다. 파일 하나만 검사하면 다른 분야를 가리키는 `overlaps`가 오류로 나오고, 레시피의 `- 도구:` 줄에 적힌 id도 전체를 돌려야 검사된다.
6. **레시피를 맞춘다.** 레시피에 쓰인 도구가 빠지거나 설치 방법이 바뀌었으면 레시피를 고친다. 레시피의 순서와 "써 보니" 기록은 실제로 해 본 경험이 우선이라, 조사 결과만 보고 순서를 바꾸지 않는다.
7. **색인과 데모를 다시 만든다.**
   ```bash
   python scripts/build_demo.py
   ```
8. **평가를 다시 돌린다.** `evals/`의 케이스를 skill-creator 절차로 돌려 통과율과 토큰을 지난번과 비교한다. 새 분야를 넣었으면 그 분야 케이스를 하나 이상 추가한다.
9. **커밋한다.** 메시지 첫 줄은 `Refresh catalog: <분야> (<기준일>)`.

## 새 분야를 추가할 때

1. `catalog/<new-area>.yaml`을 빈 목록으로 만들고 `SCHEMA.md`의 `area` 값 목록과 `scripts/check_catalog.py`의 `AREAS`에 더한다.
2. `research-prompt.md` 틀로 조사한다. 그 분야에서 꼭 다룰 하위 주제를 3~6개 적어 넘긴다.
3. 레시피가 하나 이상 생길 때까지는 SKILL.md가 그 분야를 "검증 안 된 분야"로 다룬다(추천은 하되 레시피 실행은 하지 않는다).

## 하지 말 것

- 한 사람의 블로그나 영상 하나를 그대로 카탈로그로 옮기기
- awesome 목록에만 있고 저장소를 확인하지 못한 도구 넣기
- 조사 에이전트에게 "설치해서 확인해 봐"라고 시키기
- 기준일 없이 갱신하기
